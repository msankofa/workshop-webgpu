## Next task: not all settings save to the slot states

User's words: *"investigate why not all settings save to the session states. this was a pre existing
problem."* **Pre-existing — not caused by the tab refactor.** Nothing has been investigated yet;
the notes below are structural orientation only, not findings.

### How the save/load system is built

`bot-viewer-slots.js` provides `createSlotSection({ group, label, capture, apply, slots, storage })`.
Three independent slot sets, wired at `bot-viewer-v2.html:13709-13711`:

| Group | Capture | Apply | Scope |
|---|---|---|---|
| `maze` | `captureMazeState` (13332) | `applyMazeState` (13345) | map geometry + terrain; loading rebuilds the layout and clears bots |
| `bots` | `captureBotState` (13386) | `applyBotState` (13425) | AI tuning; retunes the live roster in place |
| `ui` | `captureUiState` (13514) | `applyUiState` (13572) | camera, debug overlays, look/theme, audio; never touches the sim |

- Storage: `localStorage`, prefix `pcw:bv2:slots:` + group. `SLOT_COUNT = 6`.
- `assignKnown(target, source, keys)` copies only keys the live object already has, so a stale key
  from an older slot can't reach the settings objects.
- Reads are guarded coerces (`numOr`, `boolOr`, `clampOr`) because slot JSON is untrusted
  (hand-edited, or written by an older build).

### The structural suspicion to test first

All three capture functions **enumerate their fields by hand**. `captureBotState` is a literal object
listing ~30 named fields; `captureUiState` likewise. There is no registry tying a control to its
persisted field. So the failure mode this design invites is: a control gets added to the panel, and
nobody adds a matching line to the capture function — it works, it tunes the sim, and it silently
isn't saved. That would produce exactly "not all settings save" with no error anywhere.

If that's the cause, the fix is a choice between (a) auditing and patching the gaps once, or
(b) a control registry so a control declares its own persistence — note
`slider-state-presets-shipped` memory says the environment viewer already solved a similar problem
with a shared `controlRegistry`, which may be the precedent to reuse.

**Do not assume this is the cause.** Other candidates worth ruling out before committing: a field
that is captured but dropped on apply; `assignKnown` silently discarding a key whose live object
doesn't have it yet (initialisation order); a value read from a DOM input rather than the state
variable (e.g. `spawnCount: teamBotCountInput.value`); and the visuals look state, which round-trips
through `visuals.getLookState()` rather than being enumerated here.

### Suggested first step

Ask the user which settings they've noticed not surviving a save/load — that narrows three large
capture functions to one, and distinguishes "never captured" from "captured but not re-applied"
immediately. A mechanical diff of panel controls vs. captured fields is the fallback if they don't
have specifics.

### What the refactor did change here (so it isn't mistaken for the bug)

- `captureUiState` now reads section states from `ctrlRoot`, not `panelBody` — the pinned Bot readout
  card lives in the chrome, outside the scroller, and would otherwise be missed.
- The `ui` group gained three fields: `activeTab`, `pinned`, `compact`.
- `panel.pinned` is only applied when `Array.isArray` — a pre-refactor slot leaves pins alone.
- Old slots still load: `applySectionStates` only touches sections it finds, so renamed/removed
  cards (`Bot controls`, `Maze structure`, `Visuals`, `Audio`, `Nav grid (Phase 2)`, `Camera`) are
  ignored rather than erroring.

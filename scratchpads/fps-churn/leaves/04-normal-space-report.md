# The forest's lighting normal was in the wrong space (2026-09-09)

Claims are labelled **[source]** (read in a file in this repo), **[wgsl]** (read in shader text
generated by `node test-forest-leaf-shaders.mjs --dump`), or **[inferred]**.

## The defect

**[source]** `NodeMaterial.setupNormal` (`vendor/three-0.184/three.webgpu.js:21595`) returns
`vec3( this.normalNode )` unchanged, and `normalView` (~:15000) consumes that value directly — no
matrix, no back-face flip. A `normalNode` therefore has to be a **view-space** normal already.

**[source]** `forest-gpu.js` `instanceNodes()` produced `nRot`, the instance's yaw-rotated *local*
normal, and every role material assigned it: `leafMat.normalNode = n0Leaf.nWorld` and the seven
others (`forest-gpu.js:888-904` before this change).

**[wgsl]** Before, `scratchpads/fps-churn/leaves/wgsl/legacy-leavesL0-fragment.wgsl:233-239`:

```wgsl
normalView = vec3<f32>( ( ( normalLocal.x * nodeVar1 ) + ( normalLocal.z * nodeVar2 ) ), normalLocal.y, ... );
...
nodeVar10 = dot( normalView, nodeVar9 );      // nodeVar9 is the light direction, in VIEW space
```

`cameraViewMatrix` appears in that fragment only on a position and on the light vector, never on the
normal. So the shading dot product mixed a world/object-space normal with a view-space light.

**[inferred]** The consequence: the view matrix's rotation is the camera's, so as the camera yaws the
light direction rotates in the normal's frame. The lit side of a tree tracks the camera, not the sun.
The forest meshes sit at the origin with identity world matrices (`forest-gpu.js` `drawMesh` never
sets a transform; positions come from the draw storage buffer, and the render-origin rebase is applied
on the compute side via `uWorldOrigin` — **[source]** `base-game-forest.js` `syncOrigin`), so object
space and world space coincide for them and the only missing step was the camera one.

## The correction

**[source]** `forest-gpu.js` `instanceNodes()` now reads:

```js
const nRot = vec3(nx.mul(cy).add(nz.mul(sy)), ny, nz.mul(cy).sub(nx.mul(sy)));
const nOut = normalSpaceView ? transformNormalToView(nRot) : nRot;
const nWorld = normalVarying ? (normalSpaceView ? normalize(varying(nOut, 'v_forestNormal')) : varying(nOut, 'v_forestNormal')) : nOut;
```

`transformNormalToView` is three's own node (`three.webgpu.js:15087`): `modelNormalMatrix * n`, then
`cameraViewMatrix.transformDirection(...)`. It is used as designed rather than hand-rolled, so a
future forest group with a non-identity matrix stays correct.

**[wgsl]** After, `viewspace-leavesL0-vertex.wgsl:88` — one line, in the VERTEX stage:

```wgsl
varyings.v_forestNormal = normalize( ( render.cameraViewMatrix * vec4<f32>( ( object.nodeUniform9 * vec3<f32>( ( ( normalLocal.x * nodeVar1 ) + ( normalLocal.z * nodeVar2 ) ), normalLocal.y, ( ( normalLocal.z * nodeVar1 ) - ( normalLocal.x * nodeVar2 ) ) ) ), 0.0 ) ).xyz );
```

(`object.nodeUniform9` is `modelNormalMatrix`; the line directly above it is three's own
`v_normalViewGeometry`, built the same way.) **[wgsl]** and in the fragment stage, line 219:

```wgsl
normalView = normalize( v_forestNormal );
```

No `cameraViewMatrix` on the normal path in the fragment, no storage binding, no draw-record load —
the point of the earlier varying fix is kept.

## What the user should see

Stand still under a low sun, look at one tree, and turn the camera a quarter turn.

- `?leafnormal=world` (or the panel set to World space): the bright side of the canopy swings with
  you — after a 90-degree turn the tree is lit from a different side than it was. **[inferred]**
- default (`view`): the bright side stays where the sun is; only the shading you see of it changes
  as your viewing angle changes. **[inferred]**

Bark shows this more legibly than leaves, because trunks are round and the leaves are flat cards.

## Normalization

`transformDirection` normalizes in the vertex stage, but interpolation across a triangle shortens the
result, so the fragment gets an unnormalized vector — and unlike its own geometry normal, three does
**not** normalize a custom `normalNode` (**[source]** `setupNormal` returns it as-is). Neither the old
form nor the varying fix normalized it either. I added one `normalize()` in the fragment (**[wgsl]**
line 219 above): one op, no buffer load, and it matters most at leaf-card edges and on the interpolated
bark normals where the shortening is largest. The `world` form is left unnormalized on purpose so it
reproduces today's shader exactly for the A/B.

## Double-sided leaves

L0 leaves are `DoubleSide` (**[source]** `forest-gpu.js` `makeMat`, the hardcoded exception outside the
"Tree leaves double-sided" toggle). A custom `normalNode` receives no back-face flip — three applies
`faceDirection` only on its own `normalView` path — so a card seen from behind lights with its FRONT
normal. That was true before this change and is still true: correcting the space does not correct the
facing. Side policy is untouched here. **[inferred]** In practice this reads as a canopy where some
cards are lit from the "wrong" side; fixing it means multiplying the varying by
`faceDirection` (or `frontFacing`) in the fragment, which is a separate decision about look.

## Flag and plumbing

- `createForestGPU({ normalSpace: 'view' | 'world' })`, default `'view'` (**[source]** `forest-gpu.js`).
- `BASE_GAME_FOREST_DEFAULTS.forestNormalSpace: 'view'`, in `PALETTE_KEYS` so a change rebuilds; passed
  through at construction; mirrored into `stats.normalSpace` so a capture records it.
- `base-game.html`: the setting, the forest apply-keys list, a "Instance normal space" select in Tree
  look, and `?leafnormal=world` (`?leafnormal=fragment` still selects the per-fragment A/B).

## Static-refresh allowlist

`transformNormalToView` adds `modelNormalMatrix` to the object group — already on the allowlist, and
already present anyway via three's own `v_normalViewGeometry` — and `cameraViewMatrix`, which is a
render-group uniform, not object-group. **[source, verified by test]** `test-forest-object-group.mjs`
still shows exactly one mat3 and one mat4 in each role's object group and accepts all nine roles.
Nothing was widened.

## Unverified

The browser look. Everything above is source and generated WGSL; no frame has been rendered with the

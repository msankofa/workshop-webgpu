WebGPU: Comparing Parallelism Over Serial Execution in Web Graphics

A synthesis of five recent studies on the WebGPU/WebGL transition, reframed around a single thesis: the value of WebGPU is the replacement of WebGL's serial, stateful, per-object submission model with an explicit, parallel, GPU-driven one — and a concrete plan to migrate a procedural creature world onto it.

Procedural Creature Workshop — Engine Research Track. June 2026.

Extended background + implementation plan 5 primary sources (2024–2025) Three.js · WebGPURenderer · TSL

Abstract

WebGL has been the dominant browser graphics API for over a decade, but its programming model is fundamentally serial: a stateful machine that binds and draws one object at a time, with no general-purpose compute and a high per-draw CPU cost. WebGPU, designed against modern explicit native APIs (Vulkan, Metal, Direct3D 12), exposes a fundamentally parallel model — stateless pipelines, command encoders, compute shaders, read/write storage buffers, and indirect draw — that allows both rendering work and the decisions about what to render to move onto the GPU.

We synthesize five recent studies spanning empirical benchmarks [3][5], draw-call consolidation [1], automated migration [2], and GPU-driven terrain level-of-detail [4]. A consistent picture emerges: WebGPU's gains are smallest for trivial workloads (where its higher setup cost dominates) and largest precisely where serial WebGL stalls — many objects, large data, and iterative GPU work. The recurring engineering lever is the elimination of redundant CPU↔GPU communication by batching serial draws into parallel ones and by keeping culling and level-of-detail selection resident on the GPU. We close by translating these findings into a four-stage plan to migrate a draw-call-bound procedural world (chunked terrain, hundreds of grass and tree meshes) onto Three.js's WebGPU backend, with the literature's caveats — setup overhead, buffer-upload synchronization stalls, and the absence of tessellation and geometry shaders — built into the design.

1. Introduction

The performance ceiling of a real-time web renderer is rarely reached at the level of individual triangles. In practice it is reached at the boundary between the CPU and the GPU: how many independent commands the CPU must record and submit each frame, and how much data crosses the bus to do so. WebGL, the incumbent API, structures this boundary serially. It is a stateful machine modeled on OpenGL ES 3.0 (2010): the application binds a program, binds buffers and uniforms, issues a draw, and repeats — once per object — with the driver validating state on each call. There is no mechanism for the GPU itself to decide what to draw, and no general-purpose compute stage; data-parallel work must be smuggled through the rasterization pipeline via transform feedback or render-to-texture.

WebGPU is the first browser API designed against the explicit, parallel native APIs that displaced OpenGL on the desktop. Its pipelines are immutable, pre-validated objects; commands are recorded into encoders and submitted in bulk; and — decisively — it adds first-class compute shaders, read/write storage buffers, and indirect draw and dispatch. These primitives let an application express not only "draw this," but "compute, in parallel on the GPU, which things to draw, then draw exactly those" — with the CPU stepping back from the per-object loop entirely.

This chapter argues that the most useful frame for evaluating WebGPU is not a feature checklist but this serial-to-parallel axis. We first characterize the two execution models (§2–§3), then synthesize the recent literature against that frame (§4), and finally apply the result to a concrete, draw-call-bound application: a procedural creature world whose terrain and vegetation currently scale their cost linearly with the number of visible chunks (§5–§6).

2. The Serial Execution Model of WebGL

WebGL inherits OpenGL's stateful contract. The context is a global machine whose behavior at any draw call depends on the cumulative effect of prior bind*, uniform*, and enable calls. Three consequences define its serial character:

Per-object submission. Rendering n distinct objects requires O(n) CPU-side command sequences — re-binding state and issuing a separate draw for each. The driver re-validates much of this state per call. As object count grows, the CPU becomes the bottleneck long before the GPU's arithmetic units are saturated; the GPU spends frames waiting on a CPU that is serially narrating the scene.

No compute stage. WebGL (through 2.0) has no compute shaders and no random-access read/write buffers (SSBOs); its uniform buffers are read-only from the shader's perspective. Any data-parallel algorithm — particle simulation, instance generation, culling — must be expressed indirectly through transform feedback or by encoding state into textures and bouncing it through fragment passes. This is awkward, limited, and, as the measurement literature shows, frequently re-transfers data across the bus on every iteration [3].

The GPU cannot decide. Because there is no indirect draw, the set of draws each frame is fixed on the CPU. Visibility culling and level-of-detail selection are therefore CPU responsibilities, and their results must be marshaled back into draw calls the CPU issues one by one.

The serial model is not "slow" in an absolute sense — it is slow in proportion to scene complexity. Its costs are dominated by the count of independent CPU→GPU transactions, not by the size of any single one.

3. The Parallel Execution Model of WebGPU

WebGPU is modeled on Vulkan/Metal/D3D12 and is stateless at the point of drawing. The application builds immutable, pre-validated GPURenderPipeline and GPUComputePipeline objects ahead of time; per frame it records commands into a GPUCommandEncoder and submits them in bulk. The same redesign that reduces driver overhead also opens four parallel capabilities absent from WebGL:

CapabilityWebGPUWebGL2Why it matters here
Compute shadersFirst-class workgroup dispatchNone (faked via transform feedback)Generate/cull grass & particles on-GPU
Storage buffers (read/write)Yes (SSBO-equivalent)Read-only UBOs + texturesBuild instance lists, LOD queues on-GPU
Indirect draw / dispatchdrawIndirect, dispatchIndirectNoneGPU decides the draw count; CPU exits the loop
Render bundles & bulk submissionPre-recorded command reusePer-call state bindingCuts CPU frame time — the real bottleneck

The conceptual shift is that the decision work — which nodes are visible, at what detail, which blades survive a distance cull — can be expressed as parallel passes over storage buffers, with the surviving work fed straight into an indirect draw. The CPU's role contracts from "narrate every object" to "record a handful of passes and submit."

Two structural limits must be stated up front, because they shape every design that follows. WebGPU has no tessellation shaders and no geometry shaders. Techniques that rely on hardware tessellation to refine a coarse mesh on the fly (a common terrain-LOD strategy) must be re-expressed as compute-driven mesh selection plus vertex displacement. And the setup cost of acquiring an adapter and device is higher than WebGL's context creation — a one-time penalty that is irrelevant to a persistent application but, as we will see, dominates micro-benchmarks.

4. Synthesis of the Literature

We organize five sources around the serial-to-parallel thesis rather than chronologically. Two establish that the parallel model outperforms the serial one and under what conditions (§4.1); one isolates the dominant engineering lever — collapsing serial draws into parallel batches (§4.2); one studies the migration path between the models (§4.3); and one demonstrates the endpoint, a fully GPU-driven parallel pipeline for terrain (§4.4). Section 4.5 draws the threads together.

4.1 Empirical comparison: parallel vs serial execution

Sengupta et al., "From WebGL to WebGPU: A Reality Check" [3] (IMC '25) is the most careful general-purpose measurement to date, benchmarking 18 PolyBench/CHStone kernels across WebGPU, WebGL, WebAssembly, and JavaScript. Three findings are directly load-bearing for our thesis:

  • Setup overhead penalizes small work. WebGPU carries a roughly fixed ~0.2 s adapter+device initialization (≈0.1 s each), about twice WebGL's context setup; for small inputs WebGL is typically >25% faster, and both lose to plain CPU code. The parallel model only earns its keep once there is enough work to amortize startup.
  • Parallelism wins at scale. For large inputs, performance is dominated by GPU execution, and WebGPU's explicit control over workgroup thread counts lets it exploit parallelism WebGL cannot. WebGPU shows a slower growth rate of execution time with input size — i.e., it scales better even when an absolute crossover has not yet been reached.
  • Serial re-transfer is WebGL's structural tax. For loop-centric kernels (Jacobi, FDTD, Heat-3D, etc.), WebGPU runs >37% faster, because WebGL must re-transfer the working set across the bus on every loop iteration — the serial model made explicit. Notably, several WebGL kernels suffer context loss (GPU memory exhaustion) at large inputs on commodity hardware.

Fransson, Hermansson & Hu, Godot WebGPU vs WebGL [5] (IEEE GEM '24) moves from kernels to a real game engine, comparing WebGPU and WebGL rendering backends across real games and synthetic rasterization stress tests. The results are unambiguous and, for our case, the most relevant of the set:

Two qualitative observations matter most. First, the wins are pronounced in CPU frame time, which the authors attribute to WebGPU's modern drivers, bundled state, and stateless syntax that "leads to fewer API calls" — i.e., the elimination of serial per-object submission overhead. Second, WebGL exhibits far more stalling and frame-time variance; under load the CPU sits waiting for serial GPU instructions to retire. The one cautionary note: at the extreme (50k full-screen quads), a large per-frame upload to the instance buffer can force a CPU↔GPU synchronization even on WebGPU — a reminder that parallelism is undone by careless buffer traffic.

FindingWebGPU's advantage is not uniform — it is a function of workload. It is smallest (or negative) for trivial scenes, and largest exactly where serial WebGL is weakest: high object counts, large buffers, and iterative GPU work. The dominant gains land in CPU frame time, the very axis on which a draw-call-bound application is limited.

4.2 Consolidating serial communication: draw-call batching

If §4.1 establishes the "why," Bi et al., FusionRender [1] (WWW '24) supplies the dominant "how." Its premise is that naïve WebGPU ports underperform because they preserve WebGL's habit of rendering each object individually — "the individual rendering of each graphic leads to redundant communication between the CPU and GPU." FusionRender attacks this directly:

  1. Signature. Each object is reduced to a signature capturing everything that determines its render pipeline: vertex attribute layout, shaders, fragment target, primitive topology, depth-stencil, and multisample state.
  2. Grouping. Objects with identical signatures are hashed into groups; a group can share a single pipeline.
  3. Merged rendering. A group's static (per-vertex) and dynamic (per-object) data are concatenated into shared buffers and drawn together, with each object's dynamic data located at draw time by its index. A pipeline cache prevents redundant pipeline/buffer creation across frames.

The payoff is a 29.3%–122.1% improvement in simulated multi-object rendering and 9.4%–39.7% in complex real scenes. Critically for our application, this is precisely the structure of a chunked world: hundreds of grass or tree meshes that differ only in position share one pipeline signature, and are therefore exactly the candidates FusionRender merges from many serial draws into one parallel batch. The paper also flags an "optimal splitting" trade-off: a single enormous merged group can starve the GPU (a "bubble") while the CPU prepares it, so a small number of medium groups can outperform one giant one — a tuning knob, not a contradiction.

Applies to usThree.js's WebGPU backend already provides much of this machinery through InstancedMesh, BatchedMesh, and automatic pipeline caching, so we adopt the principle (merge identical-signature draws; cache pipelines; tune group size) rather than re-implementing FusionRender. Where Three.js stops — generating and culling the merged instances on the GPU — is where we add compute.

4.3 Bridging the models: automated migration

Han et al., GL2GPU [2] (WWW '25) addresses a practical obstacle: the labor of porting an existing WebGL codebase. It is a runtime layer that dynamically translates WebGL calls to WebGPU, emulating WebGL's stateful contract on top of WebGPU's stateless one while opportunistically applying WebGPU optimizations. Across three benchmarks it achieves an average 45.05% frame-time reduction while preserving visual output.

We do not adopt GL2GPU — our path is a native rebuild on Three.js's TSL/node materials, not a translation shim. But the result carries two lessons. First, it quantifies a floor: if even mechanical, semantics-preserving translation of serial WebGL recovers ~45%, a native parallel rewrite that restructures the work (compute culling, merged draws) should comfortably exceed it. Second, it confirms that the serial habits encoded in a WebGL application are the thing being optimized away — the translator's wins come from mapping redundant serial state changes onto WebGPU's cheaper bulk model.

4.4 The parallel endpoint: GPU-driven terrain LOD

Yuan, Wang & Ai [4] (SPIE RSMIP '25) demonstrates the fully parallel destination for one subsystem. Traditional terrain renderers run level-of-detail and frustum culling on the CPU via recursive quadtree traversal, then ship the survivors to the GPU — the serial pattern again, with the added cost of per-frame CPU↔GPU transfer. Their method moves the entire decision pipeline onto the GPU:

  • Linearized quadtree. Nodes are encoded as 64-bit Morton (Z-order) keys (stored as two 32-bit halves, since GPUs lack 64-bit integers), with a leading marker bit encoding the level. This pointer-free, linear structure is amenable to parallel, constant-time bitwise access — recursion, the enemy of GPU parallelism, is eliminated.
  • Producer–consumer compute. A producer pass performs a breadth-first expansion of nodes into a FIFO queue in GPU memory; consumer threads perform visibility tests and LOD updates, compacting visible nodes in place via read/write indices and discarding the rest. Double-buffering the queue avoids heavyweight synchronization.
  • Roughness-aware refinement. Subdivision is driven by both view distance and a terrain-roughness texture, concentrating detail on ridges and valleys.

The reported gain is 31% in rendering efficiency with reduced CPU↔GPU bandwidth and sharper terrain features. The one element that does not transfer to WebGPU is the final stage: the paper uses hardware tessellation (glTessLevelInner/Outer) to refine patches. WebGPU has no tessellation stage, so we keep the parallel, GPU-resident node selection and replace hardware tessellation with vertex displacement of a fixed grid sampled from a height field — the substitution discussed in §6.

4.5 Cross-cutting synthesis

Read together, the five sources tell a single story. The advantage of WebGPU is not a faster triangle; it is the dissolution of a serial bottleneck. WebGL's costs scale with the number of independent CPU-issued transactions — per-object draws (§4.2), per-iteration data transfers (§4.1), CPU-side culling decisions (§4.4). Every result in the corpus is a variation on moving work, or the decisions about work, off the serial CPU path and onto the parallel GPU.

The corpus is equally consistent about the boundaries of that advantage:

Recurring caveats (1) Setup overhead [3] — WebGPU pays ~0.2 s to initialize; irrelevant to a persistent app, fatal to a micro-benchmark. (2) Buffer-upload stalls [5] — a large per-frame instance-buffer upload can force CPU↔GPU synchronization even on WebGPU, re-introducing a serial stall; persistent/streamed buffers and avoiding full re-uploads are mandatory. (3) No tessellation or geometry shaders [4] — parallel LOD must be compute-driven selection + vertex displacement, not hardware tessellation. (4) Small-workload regression — for genuinely light scenes WebGPU can lose; the win is conditional on having enough parallel work to do.

The net guidance for an engine author: commit to WebGPU when the application is, or will become, heavy and many-object — and then structure the work to feed the parallel model (merged draws, compute culling, GPU-resident LOD, streamed buffers) rather than porting serial habits across unchanged.

5. Implications for a Procedural Creature World

The application under study is a browser-based procedural world: a deterministic, chunked, "infinite" terrain with streamed vegetation (grass and trees) and stylized water. Profiling under load is decisive and aligns precisely with the literature's diagnosis. At a draw distance of nine chunk-rings (361 visible chunks) the WebGL build sustains only ~18–25 fps while submitting ~600–730 draw calls over ~1,900 live geometries, with triangle count uncorrelated with the frame-rate drop. The system is not fill-bound; it is draw-call- and object-bound — the canonical serial-WebGL failure mode of §4.1–§4.2.

A within-WebGL experiment is instructive. Collapsing the 361 terrain chunks into a single instanced, shader-displaced grid removed terrain almost entirely from the draw budget (to ~1 call when frustum-isolated), yet overall frame rate improved only ~15–20%, because grass (hundreds of per-chunk draws plus main-thread geometry rebuilds) and trees remained the wall. This is the FusionRender lesson in miniature [1]: optimizing the wrong subsystem yields little; the bottleneck is the population of identical-signature draws, and the right fix is to merge and GPU-drive them — which WebGL cannot do well. The decision to migrate follows directly from the data and the corpus.

6. Implementation Plan

We decompose the migration into four sub-projects, each with its own spec, plan, and acceptance gate. The ordering banks a foundational validation first, then attacks the measured bottleneck, then the structural LOD gap, then the roadmap features that motivated the platform choice. Every stage carries the §4.5 caveats as explicit design constraints.

SP1 — Renderer migration foundation first · complete ✓

Goal. Replace WebGLRenderer with WebGPURenderer and port all existing materials (terrain, grass wind/fade, water caustics, clouds) to TSL/node materials so the scene renders identically on WebGPU — no new features. This is the "reality check" [3][5]: confirm parity and measure the CPU-frame-time win on target hardware before building on it.

Key risk. The codebase's shader strategy is GLSL onBeforeCompile injection (terrain displacement, water caustics). This does not exist in TSL — the node model replaces it. Each injected effect must be re-expressed as TSL nodes. This supersedes the in-flight WebGL heightmap-terrain shader work, which becomes a reference, not the path.

Gate: visual parity with the WebGL build (terrain, lakes, caustics, grass, clouds); a perfStats trace at draw distance 9 showing CPU frame time at or below the WebGL baseline; documented adapter/device setup time (expected ≈0.2 s, one-time).

SP1 result · measured Status: complete. Migrated to Three.js r0.184.0 (three/webgpu + three/tsl) behind a ?renderer= flag for side-by-side comparison. Grass, clouds, and water were ported to TSL node materials: water surface (wave normal, Fresnel, depth), planar reflection via the TSL reflector() node, refraction via viewportSharedTexture, and animated caustics. The key risk landed exactly as predicted — the GLSL onBeforeCompile caustic projection has no TSL equivalent, so it was re-expressed as a render-to-target caustic-texture node contributing additively to a MeshStandardNodeMaterial terrain. Adapter+device renderer.init() measured 217 ms on target hardware, matching the ≈0.2 s one-time setup the literature flags [3] and confirming caveat (1) is a non-issue for a persistent app.

One follow-up stays open: procedural (canvas-generated) tree textures fail to bind on the main pass under the node-material texture lifecycle (tracked as issue 001); authored textures — the production default — are unaffected, so SP1 ships on them.

SP2 — GPU compute grass the bottleneck

Goal. Replace per-chunk CPU-built grass meshes with a compute-driven, indirectly-drawn instanced system: a compute pass generates per-blade instance transforms in a camera-centered region (deterministic per-cell seeding to preserve placement), performs frustum + distance culling into a storage buffer, and writes drawIndirect arguments; a single instanced draw renders the survivors. Distance density falls out continuously from the cull, replacing the per-blade shader-fade hack.

Informed by. FusionRender's merge-identical-signatures principle [1] (hundreds of grass draws → one) and the §4.1 result that compute + storage buffers are where WebGPU's parallel advantage is largest [3].

Caveat wiring. Per §4.5, avoid full per-frame instance-buffer re-uploads (the GEM'24 stall [5]): the instance/argument buffers are GPU-resident and updated by compute, never re-uploaded from the CPU.

Gate: grass draw calls become O(1) regardless of chunk count; triangle count tracks visible blades, not the global budget; no main-thread geometry rebuild while streaming; a draw-distance-9 trace showing the grass-dominated frame-time wall removed.

SP3 — GPU-driven CDLOD terrain structural LOD

Goal. Adopt the parallel terrain pipeline of §4.4 [4], adapted to WebGPU's lack of tessellation. A linearized (Morton-keyed) quadtree is held in a storage buffer; a producer/consumer compute pass selects visible nodes and LOD levels on the GPU and emits indirect draws. Hardware tessellation is replaced by vertex displacement of a reusable grid sampled from the height field — directly reusing the existing parity-tested heightmap groundwork (bilinear-correct sampling, symmetric tile aprons for seamless edges and normals). Continuous LOD morphing in the vertex stage prevents popping.

Informed by. §4.4's GPU-resident node selection + culling; the project's own heightmap parity work supplies the displacement source of truth, guaranteeing visual/collision agreement by construction.

Gate: terrain triangle and draw-call cost bounded and roughly constant versus draw distance (not just collapsed, as in the WebGL instanced experiment); no cracks or popping across LOD seams; collision still served by the analytic height field; a trace showing terrain cost flat from draw distance 4 through 12.

SP4 — Lights, effects, and post-processing roadmap drivers

Goal. Deliver the visual roadmap that justified the platform choice: many dynamic point lights via clustered/tiled forward lighting (feasible only with compute + storage buffers), GPU-driven particle/effect systems, and a node-based post-processing stack (bloom, AO, color grade) — all native to the WebGPU backend and infeasible or expensive under serial WebGL.

Informed by. The whole corpus: each feature is a many-object or compute-heavy workload, the regime where §4.1/§4.5 place WebGPU's advantage; clustered lighting is the canonical "decide on the GPU" pattern.

Gate: target dynamic-light count rendered within frame budget; post stack composited without reintroducing CPU-bound passes; measured against the SP1 baseline.

Sequencing rationaleSP1 is foundational and validating (cheap to abandon if WebGPU disappoints on target hardware). SP2 attacks the measured bottleneck and proves the compute pipeline. SP3 closes the one structural gap WebGL never had (true LOD). SP4 cashes in the roadmap. Each stage is independently shippable and gated on a perfStats trace, preserving the measure-then-commit discipline that selected WebGPU in the first place.
